# nf-imputation-pipeline

GitHub repository for an imputation pipeline implemented in Nextflow. This documentation and pipeline are actively undergoing construction. Note that while the pipeline can currently impute input array datasets, tests are currently being developed to ensure accurate and correct outputs generated by processes.

While documentation and tests are being developed for low pass WGS inputs, the pipeline is currently unavailable for lcWGS/lpWGS data. Note that if needing to run both array and lcWGS data, these runs will need to be performed in separate project directories.

If the pipeline is used for analysis, please cite the appropriate tools - citations are provided at the end of the document.

## Overview of nf-imputation-pipeline

* Workflow image coming soon

The Rowan lab `nf-imputation-pipeline` aims to impute genotypes from array or low-pass whole genome sequencing datasets to provided haplotype reference panels. 

Please see "Modifying the Configuration File" for modifying defaults. 

## Preparing to Run the `nf-imputation-pipeline`

In order to run the pipeline, you must have the following inputs:

- Nextflow configured on your system (designed for SLURM-based schedulers)
- Input sample(s) that require imputation (BCF/VCF(.gz) with associated index (.csi))
- Reference panel(s) for imputing (BCF/VCF(.gz) with associated index (.csi))
- Sample and reference metadata for downstream processes

Input samples that require imputation will be referred to as test samples throughout this documentation. The test samples are assumed to be a BCF/VCF(.gz) file that contains multiple individuals. The reference population that you are using to impute with will be referred to as the reference panel. The user may optionally provide genetic maps for recombination rates used for phasing and imputation steps.

## Quickstart

Please be aware that modifying, adding, or changing file structure can cause the pipeline to not work as intended, and is only suggested for those very familiar with Nextflow and the tools used within this pipeline! 

For users with experience with Nextflow and using a SLURM-based high-performance computing system, navigate or create your desired project directory and clone this repository. Then, create your test sample metadata sheet and reference panel metadata sheet as described in [Sample and Reference Files and Metadata](https://github.com/maddiehenniger/nf-imputation-pipeline?tab=readme-ov-file#sample-and-reference-files-and-metadata). Once complete, modify the `nextflow.config` file to supply the required fields. Nextflow will detect the files from the provided metadata sheets and start the pipeline.

Clone the GitHub repository. 

```
git clone https://github.com/maddiehenniger/nf-imputation-pipeline.git
```

Navigate into the cloned respository.

```
cd nf-imputation-pipeline
```

Modify the `nextflow.config` file to provide paths to your metadata sheets and supply a project title. Please make sure to fill out the appropriate information required for the pipeline to run. No matter the input data type, the `nextflow.config` file must be provided: `projectTitle`, `samplesheet`, `dataType` (default is 'array'), `references`. If data type is array, please provide the `phasingModel`. If data type is `lpwgs`, please provide the `glimpse2Model` - the user may also additionally provide a path to the `fastaReference` for GLIMPSE2. More details are available at [The Configuration File](https://github.com/maddiehenniger/nf-imputation-pipeline#the-configuration-file).

If you are not running this pipeline on the University of Tennessee's ISAAC HPC, you will need to modify the SLURM parameters in the `conf/isaac.config` file. See [Preparing to Run on a Cluster](https://github.com/maddiehenniger/nf-imputation-pipeline/tree/main?tab=readme-ov-file#preparing-to-run-on-a-cluster) for more detail.

Once the `nextflow.config` file is populated, the user may elect to modify the default parameters available in the `/conf/args.config` file, if desired for their relevant tasks. 

To start, create a script in the project directory (ex: `touch nf_run_pipeline.sh`, then edit the file). Then, add the appropriate headers for the SBATCH script. Note that depending on availability, the user may need to allow extra time for the main script submission to run. The `nextflow run main.nf` can be added. For example, below, where the profile is configured for `condo_trowan1` (applicable for most internal members). Plugins are specified in the example, as well as an additional parameter to limit the number of jobs submitted at once (`-qs 5`). This value could be increased if the user would like to submit more jobs. The user may also supply in the configuration file if specific nodes should be left available for use on their HPC.

```
nextflow run main.nf -profile condo_trowan1 -plugins nf-schema@2.1.0 -qs 5
```

This will start a job submission that will spawn the subsequent jobs to run the pipeline. The jobs are spawned as long as the main SBATCH submission is running, so please be sure to provide enough time for the analysis to be completed. The jobs that are spawning as the pipeline are generated are controlled by individual resources specified and are not impacted by the amount of memory or CPUs dedicated to the initial SBATCH submission. If the pipeline exits due to time constraints, the user may provide the `-resume` option to the `nextflow run...` script, which will use cached files present to "catch up" to where the pipeline exited. Note that if any of the files or parameters are modified in between a pipeline exiting and the user supplying `-resume`, there may be inconsistencies in the files generated. Modifications should likely require the pipeline to be entirely restarted. Use `-resume` with caution. 

All of the imputed samples will be deposited in the `/data/final_imputed_samples/` directory generated during the pipeline and finalized after completion. Here, the samples will be named as `{sampleID}.{imputationRound}.ligated.{chromosome}` and be in BCF format with their associated indexed files (ex: test_sample.one.ligated.19.bcf would be for the user-provided sample named test_sample, after one round of imputation, ligated after chunking steps for chromosome 19, in BCF file format). If performing two rounds of imputation, as provided by the reference metadata sheet, there will also have a second sample with the same initial sampleID (ex: test_sample.two.ligated.19.bcf).

The user may track job progress in the file generated after the pipeline begins, located in the `sbatch_logs` directory. This is also where error messages will populate if the pipeline does not run correctly. 

Once the pipeline is completed, the user may then delete intermediate files generated throughout the pipeline using `nextflow clean`. The user may first use `nextflow clean -dry-run` if desired to see which Nextflow work directories will be removed before running the cleanup option. To remove the intermediate files generated, specify `nextflow clean -f`. This removes all intermediate files generated throughout the pipeline from the last run and retains the files located in `/data/final_imputed_samples/`. Cleanup is not performed automatically so that the user may inspect intermediate files generated throughout the pipeline, but intermediate files may consume a lot of storage on the user's quota and cleanup is recommended. Note that the cleanup will be done on a run-by-run basis, so if the job is submitted multiple times, different clean options may be necessary.

### Required Input Files

The following are the user-required files for the pipeline to work. Please note the required input file extensions, expected file format, and pipeline assumptions for each file type. IMPORTANT: The input files for this are assumed to be in BCF/VCF(.gz) format and have already been filtered for the analysis-appropriate quality, allele frequencies, missingness, etc., if relevant to the analysis. The user must make sure their chromosomes match the chromosome IDs present in the reference panel. The user must be aware of how including low-quality base calls in the dataset may impact downstream imputation accuracies. These assumptions apply to the test sample populations and reference panel populations provided. 

The pipeline will automatically detect where the user's test sample(s), reference(s), and optionally, genetic map(s) are located using the user-provided metadata sheets that are specified in the `nextflow.config` file. For details on how to populate these, please see below sections.

#### Sample and Reference Files and Metadata

The input test file(s) containing individuals to undergo imputation may either be in BCF/VCF file format and can optionally be gzipped (ending in .gz) when performing imputation following the 'array' or 'lpwgs' specified data types. The indexed file(s) must be provided and are assumed to have the same naming scheme as the input file(s). Note that if providing BCF/VCF (optionally gzipped) files for 'lpwgs', the files must contain genotype likelihoods (GL field) as required by GLIMPSE2. The input file(s) provided to undergo imputation may either be in BAM/CRAM file format when performing imputation following the 'lpwgs' specified data type. However, only one file type per run may be used with the current iteration; that is, the input files cannot consist of file extensions `.bam`/`.cram` AND `.bcf`/`.vcf`/`.vcf.gz`. In the case that mixed files are provided, the pipeline will exit with a warning for the user to only supply BAM/CRAM *or* BCF/VCF(.gz) files. 

For BCF/VCF(.gz) file format, the input test file(s) have no input requirement for the number of individuals. The pipeline will impute the individuals present within each file regardless of the input number of markers, unless no markers exist for the region specified. The input test files are assumed to be unphased and there is currently no option to skip phasing. The input test file(s) should not be split by chromosome as the pipeline will detect chromosomes from samples and split accordingly. Note that, when providing multiple files, each input file provided on each line will be imputed separately. This feature is helpful when provided data across multiple arrays.

For optional requirements, include the header name in the metadata sheet, but leave fields empty. Please see `/examples/` for some examples of test sample and reference metadata.

The sample metadata should be a comma-delimited file (.CSV) containing the following columns: sampleID, samplePath, sampleIndex, pedigree
- sampleID: [required] A string with no spaces containing the user-defined name of the sample with no file extensions (ex: array_one)
- samplePath: [required] A file path to where the associated sample is located in your file system; when working with array data, this should end with the file extension `.bcf`, `.vcf`, or `.vcf.gz` (ex: `/path/to/sample/array_one.vcf.gz`) or `.bam`/`.cram` if working with lcWGS data (ex: `/path/to/sample_1.bam`). Note the exception that BCF/VCF file format may be used for lcWGS if the file contains genotype likelihoods (GL) FORMAT field
- sampleIndex: [required] A file path to where the associated sample's indexed file is located in your file system; when working with arrays, this should end with the file extension `.csi` (ex: `/path/to/sample/array_one.vcf.gz.csi`) or `.bai`/`.crai` indexed file if working with lcWGS data. Note the same exception above that BCF/VCF file format may be used for lcWGS if the file contains the GL format field, where the associated index file would also end in `.csi`
- pedigree [optional] An optional file path to where the associated sample's pedigree information is located in your file system; this should end with the file extension `.fam`, `.txt`, or `.tsv` (ex: `/path/to/sample/pedigree_array_one.fam`) and contain one line per sample having parent(s) in the dataset and three tab-delimited columns containing kidID fatherID motherID. See below and the SHAPEIT5 documentation for more detail. Note that if your input dataset is following lcWGS imputation, this column should remain empty as GLIMPSE2 does not currently support phasing to pedigree information - the pedigree information will be ignored

The user may choose to optionally provide a pedigree file to perform phasing, if the appropriate information is available. The pedigree file should be formatted as directed by SHAPEIT documentation. Note that the pedigree file is currently not supported for phasing with GLIMPSE2. The IDs present in the input test sample (of format BCF/VCF, optionally gzipped) should align with the IDs present in the pedigree file. The pedigree file is a tab-delimited file ending in `.fam` that consists of three columns, which have no header. The file should contain one line per sample having parent(s) in the dataset and three columns (kidID  fatherID    motherID), separated by TABs for spaces. Use NAs for unknown parents (in the case of duos). In the output file, the first offspring haplotype is transmitted by the father, and the second by the mother. This tool uses family data to fix the phase of offspring heterozygous genotypes when possible, that is when: 1 - there is no Mendel inconsistency, and 2 - at least one parent is homozygous. In other words, it builds a scaffold of haplotypes for offsprings from the parental genomes. This information is conveyed directly from the SHAPEIT5 documentation, located [here](https://odelaneau.github.io/shapeit/docs/documentation/phase_common/#usage2-phasing-related-samples). Including the pedigree file does not prevent the user from choosing phasing to a haplotype reference panel or within sample.

The reference panel(s) must be in a BCF/VCF file format and can optionally be gzipped (ending in .gz). The reference panel should already be phased and there is no option currently to perform reference panel phasing. The reference panels must be provided on a by-chromosome basis. There are no marker or individual requirements for the reference panel(s). Users must be aware of how the number of markers and individuals may impact imputation performance. Similarly to the test sample metadata, if the user does not wish to provide an optional column, the column name must exist but the field may remain blank.

The reference metadata should be a comma-delimited file (.CSV) containing the following columns: referenceID, referencePath, referenceIndex, chromosome, imputationStep, geneticMapPath
- referenceID: [required] A string with no spaces containing the user-defined name of the reference panel with no file extensions (ex: reference_chr1)
- referencePath: [required] A file path to where the associated reference panel is located in your file system; this should end with the file extension BCF/VCF(.gz). (ex: `/path/to/reference/reference_panel_chr1.bcf`)
- referenceIndex: [required] A file path to where the associated indexed file for the reference panel is located in your file system; this should end with the file extension `.csi`. (ex: `/path/to/reference/reference_panel_chr1.bcf.csi`)
- chromosome: [required] An integer in the form of a numerical value to the associated chromosome for the reference panel; at this time, sex chromosome (non-integer) values are not accepted
- imputationRound: [required] A string containing one of two values: either `one` or `two` - one should correspond to the reference panels used for the first round of imputation and two should correspond to the reference panel to use for the second round of imputation, if applicable. If only performing one round of imputation, the user does not have to supply a `two` value
- geneticMapPath: [optional] A file path to where the associated genetic maps for the specific chromosome are located in your file system, ending with the file extension gmap; if the genetic map is not provided, then the default 1 cM/Mb recombination rate is used for downstream phasing and imputation processes

The user may choose to optionally supply genetic maps containing recombination rates on a per-chromosome basis. The genetic maps are a tab-delimited file ending in `.gmap` that consists of 3 columns: pos / chr / cM:
- pos: The position in bases on the chromosome (must be in bases, not in mb, kb, etc.)
- chr: The chromosome number
- cM: Measure in centimorgans (cM) of how often recombination happens

If the genetic maps provided are not in this format, the tools will be unable to conduct phasing and imputation using the genetic maps and will return error messages and prevent further jobs spawning. If the genetic maps are not provided and are left blank, the pipeline will recognize that no recombination rates are provided and will phase/impute under the declared defaults.

### The Configuration File

The `nextflow.config` file is where the workflow configurations are located. The configuration file is automatically detected by Nextflow, provided it is not moved from within the project launch directory. The user must modify the configuration file in order for the pipeline to run. The configuration file is built for the intention of running on a SLURM-based system. Before running the pipeline, the user must modify the `nextflow.config` file. 

The following "Input/Output Options" should be filled: supply a user-defined `projectTitle` (ex: `nf-project-imputation`, `henniger-dissertation-testing`, etc.), path to the `samplesheet` (containing the test sample metadata, ex: `/path/to/samplesheet.csv`, `samplesheet.csv`), the `dataType` of either value 'array' or 'lpwgs' (where your input data is either array genotypes or low-pass whole genome sequencing data), and the path to the `references` (containing the reference panel metadata, ex: `/path/to/references_metadata.csv`, `references.csv`). Please note that the default value of `dataType` is 'array'.

If the user's input data is 'array', please select which SHAPEIT parameters to use for phasing. It is up to the user to determine the appropriate phasing parameters for the input test samples by reviewing literature and best practices with tools. A brief summary of the different options for this step are provided. These include three values that correspond to three scenarios that are described below: 'use_reference','no_reference', or 'shapeit4_no_reference'.
- 'use_reference' : SHAPEIT5_phase_common will run to perform phasing, using the reference panel declared with round 'one' for informing phasing. Note that SHAPEIT5 will only phase where there are overlapping markers present in the reference panel, meaning that if the input sample's variants do not overlap with the reference panel, these variants will be removed. In the case zero variants are present for a region, SHAPEIT5 errors will cause the pipeline to exit.
- 'no_reference' : SHAPEIT5_phase_common will run to perform phasing, without using the reference panel for informing phasing. If the user supplies an input file with <50 individuals, this will return an error by SHAPEIT5 stating that you should use a reference to inform phasing. This error will cause the pipeline to exit as the pipeline will not be able to perform imputation. If applicable and the user must perform phasing without a reference panel and cannot increase the number of input individuals, please refer to the 'shapeit4_no_reference' for the workaround scenario.
- 'shapeit4_no_reference' : SHAPEIT4 will run to perform phasing, without using the reference panel for informing phasing. This option allows the user to bypass the error in the 'no_reference' scenario regarding the number of input individuals (if the user has <50 input test individuals). Note that you still must have at least 20 individuals within the file if using this approach - there is no current workaround for non-reference phasing with <20 individuals.
Note that all of the SHAPEIT phasing modules are able to be used with or without pedigree information, provided the population meets the minimum size. If the user supplied the pedigree information in their sample metadata, the tool will use that information.

If the user's input dataType is 'lpwgs', the user must provide the 'phasingModel' for GLIMPSE2_chunk. The input must be of value 'recursive' or 'sequential'. See the GLIMPSE2_chunk documentation for more information.

These configuration inputs allows the pipeline to classify the pipeline by project, locate input test samples, locate reference panels, and allow user flexibility for managing phasing and imputation parameters.

### Modifying Parameters for Phasing and Imputation

Within the `/conf/args.config` file, the modules run throughout the pipeline will have their additional parameters available for the user to modify. All parameters provided in the `/conf/args.config` file are the default arguments for phasing and imputation. If the user would like to perform parameter exploration or modification, the defaults may be modified. Further, if there is a specific argument the user would like to add that exists for the tool but is not provided here, the user may add it here. Please note that parameter modification may be critical to improving the user's imputation accuracy.

We provide an example here, using the process labeled 'shapeit5', which runs SHAPEIT5's phase_common. Located within the `conf/args.config` file, there are a number of default parameters specified by SHAPEIT5.

```
// SHAPEIT5 phase_common parameters
        // Please see @https://odelaneau.github.io/shapeit/docs/documentation/phase_common/ for more details
        // All parameters specified below are the provided default parameters for SHAPEIT5 phase_common
        // Note that '--filter-snp' is commented out to prevent automatic application
    withLabel: 'shapeit5' {
        ext.argsDefault = [
            // Filter Parameters
            // '--filter-snp': ' ', // NA if specified, the program only considers SNPs
            // '--filter-maf': '0', // FLOAT only consider variants with MAF above the specified value. It requires AC/AN tags in VCF/BCF file
            // MCMC Parameters - Expert
            '--mcmc-iterations': '5b,1p,1b,1p,1b,1p,5m', // STRING iteration scheme of the MCMC (burnin=b, pruning=p, main=m)
            '--mcmc-prune': 0.999, // FLOAT pruning threshold for genotype graphs (internal memory structures)
            '--mcmc-noinit': 'NA', // If specified, phasing initialized by PBWT sweep is disabled
            // PBWT Parameters - Expert
            '--pbwt-modulo': 0.1, // FLOAT storage frequency of PBWT indexes in chromosome
            '--pbwt-depth': 4, // INT depth of PBWT indexes to condition one
            '--pbwt-mac': 5, // INT minimal minor allele count at which PBWT is evaluated
            '--pbwt-mdr': 0.1, // FLOAT maximimal missing data rate at which PBWT is evaluated
            '--pbwt-window': 4, // INT run PBWT selection in windows of this size
            // HMM Parameters - Expert
            '--hmm-window': 4, // INT minimal size of the phasing window in chromosome
            '--hmm-ne': 15000, // INT effective size of the population
        ]
    }
```

To modify these parameters, adjust the value after the semicolon, as shown below in an example for `--filter-maf` in SHAPEIT5 phase_common.

```
'--filter-maf': '0.00001', // FLOAT only consider variants with MAF above the specified value. It requires AC/AN tags in VCF/BCF file
```

Keep in mind that the user-supplied values still must fall in the range of accepted values for the parameter (e.g., `--pbwt-window` must be in the range of 0.5 and 10 cM). Please note that the default values do not necessarily represent an optimal value for phasing and imputation, and modifying parameters can alter the accuracy of imputation and therefore appropriate parameter exploration should be conducted to determine ideal values within the user's testing population.

### Preparing to Run on a Cluster

The current implementation of this pipeline assumes that the pipeline is being ran on SLURM-based HPC and is specialized for the University of Tennessee's HPC (ISAAC). ISAAC maintains Apptainer/Singularity in addition to Nextflow on the cluster. If not planning to run this on ISAAC, some configurations will need to be set up by the user. Please make sure Apptainer/Singularity and Nextflow are maintained in some fashion on the user's system before attempting to run the pipeline, and that the SLURM scheduler is set up correctly.

See `/conf/isaac.config`, where the user's account, partition, and condo may be specified in addition to resource usage. Resources are additionally stored in the `/conf/resources.config` file. Please ensure that the scratch directory path is correctly defined for Nextflow to store large files generated throughout the process. Once configurations are appropriately set up, the user may then create a bash script to run the Nextflow pipeline, for example at the basic level: `nextflow run main.nf -profile PROFILE_HERE -plugins nf-schema@2.1.0`. Renaming or moving files within the `nf-imputation-pipeline` directories will nearly always cause the pipeline to fail unless the user is thorough in renaming profiles/etc.

Additional arguments may be added to `nextflow run`, such as `-qs` to limit the number of submissions (ex: `-qs 5` would submit manage 5 jobs at a time), or `-resume` to use cached files to start at a later step, if the pipeline exits and can be resumed. If modifying parameters, modules, etc., please use caution if intending to use `-resume`. 

### Nextflow Directory Structure

The cloned Nextflow directory will consist of the following directories: 
- `/assets/`: Contains the schemas for the input metadata sheets, one for the references and one for the input samples. It also contains `NO_FILE` which is used to evaluate the presence or absent of the genetic maps.
- `/bin/`: Contains some tools that are not able to be pulled using Singularity/Apptainer. 
- `/conf/`: Contains numerous files associated with running and managing the Nextflow pipeline. This includes: `args.config` where the user can modify default parameters for running the pipeline; `containers.config` where Singularity/Apptainer images are declared; `isaac.config` where the SLURM-based profile is stored; `plugins.config` where specific provided plugins can be specified; `reporting.config` where configuration of reports can be specified; and `resources.config` where HPC resource management is specified. Note that the user will have to modify `isaac.config` if running on another system. 
- `/examples/`: Contains examples of formatted metadata sheets and an example of how to create an SBATCH submission script.
- `/modules/`: Contains the ground-level modules that constitute the pipeline. Modules are the smallest building block of the pipeline.
- `/subworkflows/`: Contains subworkflows that are made up of modules, and can help organize channel structure throughout the pipeline.
- `/workflows/`: Contains workflows that are made up of subworkflows..

The following files are present: 
- `main.nf`: This is the script that will run the pipeline. `main.nf`'s location allows it to detect where the processes to run are located, as well as use the configuration files to determine where files need to be saved/etc. 
- `nextflow.config`: The user needs to populate the `nextflow.config` file in order for the pipeline to successfully run. The `nextflow.config` file allows for files to be located anywhere accessible within the user's file system as long as they are correctly provided in the metadata sheets for the sample(s) and haplotype reference panel(s). The user may also provide some specific parameter tweaks here, such as modifying the phasing tools, or providing information about the generated data for the input test samples.
- `README.md`: The current file, providing documentation about the pipeline.

Once the pipeline is submitted, the following directories will be generated:
- `/data/`: Contains directories with the files and logs generated as the pipeline is conducted. Intermediate files generated throughout the process are symbolically linked where possible to allow the user to assess what occurs throughout the pipeline.
- `/reports/`: Contains the `/summary/` directory, which provides .html reports and trace reports (.txt) for resource utilization.
- `/sbatch_logs/`: Contains the output from the submitted SBATCH script; the `.out` file can be used to examine sample progress or identify potential errors occurring throughout the pipeline run. 

## Detailed Walkthrough of the Workflow

The following sections will detail the processes executed by each workflow in the Nextflow `main.nf` script.

### PREPARE_INPUTS

PREPARE_INPUTS workflow performs the following steps: 
- `parse_input_sheets.nf`: Reads in the files defined in the `nextflow.config` file from the `samplesheet` and `references` categories. Here, the existence of optional inputs are evaluated and the references are divided by the round of imputation they are associated with. If no round 'two' option is provided by the user, this becomes an empty channel that is not used downstream. The presence of absence of genetic maps are evaluated here as well. This subworkflow uses a Nextflow plugin to convert the input datasheets to a cardinality expected by Nextflow. 
- `preprocess_inputs.nf`: Takes in the samples, references for round one of imputation, and references for round two of imputation (if provided). It also uses the `dataType` specified in the `nextflow.config` file to determine what sort of pre-processing needs to be conducted. The files are preprocessed based on whether their file extension is BCF, VCF (optionally gzipped) or BAM, CRAM. The pipeline will detect at this step if multiple file types are provided, as this is not currently supported in the pipeline. If the input data is `array` (the default), the module `bcftools_identify_chromosomes.nf` is ran to identify the chromosomes present in the input BCF/VCF(.gz) file(s). This step produces a text file containing a chromosome per line. Samples are then split by the chromosomes present in their files `bcftools_split_samples.nf`. It is critical at this step that input test sample chromosomes match what is provided in the reference files. The values generated here are used to link the samples to their appropriate reference; therefore, if input sample and provided haplotype reference panel chromosomes do not match, the user may not receive imputed samples for that region or may otherwise run into errors that cause the pipeline to exit. Many of these tools require that the AC/AN tags are filled in the BCF/VCF(.gz) files, so `bcftools_fill_tags.nf` is ran to populate the AC/AN INFO tags. While the input test samples are being processed, the haplotype reference panel(s) is prepared for subsequent phasing and imputation based on the `dataType` parameter. If the `dataType` are 'array', the references are converted to the preferred XCF file format. If the `dataType` are 'lpwgs', the reference panel is "chunked" by chromosome to identify phasing/imputation buffer and imputation regions. The reference is then split into these regions for processing. At the end of the process, the test samples split by chromosome are then combined with the formatted round one reference panel for downstream phasing and imputation. 

### Phasing and Imputation

If the user's input data is 'array', the pipeline will run the declared SHAPEIT phasing option to phase the input samples provided in the samplesheet. As said earlier, it is up to the user to determine the appropriate phasing parameters for the input test samples by reviewing literature and best practices with tools. A summary of the options are provided below and there is no recommended phasing option to use. That is, we do not suggest that any specific method is the "optimal" way to perform phasing, as the input population's composition will impact the user's decision. The user may desire to test a few of these options to determine which works best for the input samples. These include three values that correspond to three scenarios that are described below: 'use_reference','no_reference', or 'shapeit4_no_reference'.
- 'use_reference' : SHAPEIT5_phase_common will run to perform phasing, using the reference panel declared with round 'one' for informing phasing. Note that SHAPEIT5 will only phase where there are overlapping markers present in the reference panel, meaning that if the input sample's variants do not overlap with the reference panel, these variants will be removed. In the case zero variants are present for a region, SHAPEIT5 errors will cause the pipeline to exit. The `use_reference` option may be helpful when the user's test population is small, as SHAPEIT5 requires a minimum of 50 input individuals for non-reference phasing.
- 'no_reference' : SHAPEIT5_phase_common will run to perform phasing, without using the reference panel for informing phasing. If the user supplies an input file with <50 individuals, this will return an error by SHAPEIT5 stating that you should use a reference to inform phasing. This error will cause the pipeline to exit as the pipeline will not be able to perform imputation. If applicable and the user must perform phasing without a reference panel and cannot increase the number of input individuals, please refer to the 'shapeit4_no_reference' for a potential workaround scenario.
- 'shapeit4_no_reference' : SHAPEIT4 will run to perform phasing, without using the reference panel for informing phasing. This option allows the user to bypass the error in the 'no_reference' scenario regarding the number of input individuals (if the user has <50 input test individuals). Note that you still must have at least 20 individuals within the file if using this approach - there is no current workaround for non-reference phasing with <20 individuals. Although there are not many major differences between the underlying model between SHAPEIT4 and SHAPEIT5, the user should understand, if selecting the `shapeit4_no_reference` option, what potential differences could impact data processing.

There are a few issues that can occur at this step that will cause the pipeline to exit. If there are no overlapping variants between the test sample and reference panel provided, there will be no variants able to be phased and this error will cause the pipeline to exit, as that outcome should indicate there could be potential problems with the input test sample. In the case that the user is running `use_reference` and obtains this error, please review the input coordinates provided to the pipeline. Ensure that REF and ALT alleles are properly ordered - there are known and documented occurences between PLINK and PLINK2 that can cause allele swaps, which may affect the input sample's ability to align to the reference panel. The user must make certain the input samples are in the correct format before input into the pipeline.
